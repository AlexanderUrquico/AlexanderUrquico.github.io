Inventory Management App

Sole developer — architecture, implementation, release

An offline-first inventory platform used across warehouse, distribution and retail branches. Staff scan barcodes to count stock, move it between locations and approve transfers; every entry is written to an on-device database first and posted to the ERP when the operator confirms. The user's role, resolved at login, decides which home screen and which workflows they ever see.

What it does

  • Barcode counting with a logged manual-search fallback for compliance
  • Receiving, store-to-store transfers, batch picking and transfer approvals
  • Batch and expiry tracking with FEFO-aware handling
  • PDF and Excel reporting with inventory-limit variance tracking
  • Four role-specific home screens: branch, warehouse, distribution, audit

How it's built

  • Layered architecture: Screens → Cubits → Repositories → SQLite
  • Offline-first sync of item master, users and count periods
  • Hashed credentials, encrypted secure storage, centralised validation
  • Structured logging with sensitive-data masking
  • Architecture, security and contributor guides maintained in-repo

Deposit Slip Uploader

Sole developer — architecture, implementation, release

A native Android app that closes the gap between a branch depositing cash and finance seeing proof of it. Staff photograph the deposit slip and on-device OCR reads the bank, reference number, amount and date straight off the paper — so the person submitting confirms fields instead of typing them. It replaced a paper trail that used to travel by courier and arrive days late, if at all.

What it does

  • On-device text recognition that auto-fills deposit fields from a photo
  • Bank-specific parsing rules, because every slip layout is different
  • Up to three slips per submission, with edit-and-resubmit for corrections
  • Authenticated sign-in against the central user directory
  • Configurable server endpoint, so branches on different hosts share one build

How it's built

  • Jetpack Compose UI with Navigation Compose
  • ML Kit text recognition running fully on-device — the photo is processed locally
  • Retrofit + OkHttp multipart client, Gson serialisation
  • Image downscaling and JPEG compression before upload for low-bandwidth branches
  • Local SQLite cache and scoped FileProvider sharing

Warehouse Transfer App

Sole developer — discovery, architecture, prototype

A ground-up replacement for the transfer module of a legacy desktop application, aimed at pickers who are on foot in the aisles while the PC is not. I ran the discovery myself: audited the old system, documented what it actually did, and found the defects that would justify a rewrite — including a validation check reading the wrong quantity field, which had been quietly allowing over-transfers, and a submission path that could create two real documents for one physical movement.

What I decided and why

  • Writes go through the ERP's official service layer, never direct SQL — business rules and support coverage stay intact
  • Submissions land in a staging outbox first, which makes a duplicate posting structurally impossible
  • Reads run through stored procedures so listing stock doesn't consume an ERP licence
  • One module first, running beside the old app until it's proven
  • Recorded the rewrite as not yet formally justified — several issues were fixable in place, and I said so

Where it stands

  • Authentication working end to end against live company data: picker directory, first-time PIN enrolment, sign-in, lockout after repeated failures, supervisor-gated admin
  • Picking, scanning and submit flows built against a mock repository behind the same interface, ready to switch over
  • Shipped with a phased roadmap, endpoint contract, staging schema and a status doc so anyone can pick it up

How I work

Read the system before rewriting it

Most of my work happens inside systems that are already running and already load-bearing. That shapes how I approach it.

01 — Find the real problem

Before proposing a rewrite I audit what exists and write down what it actually does. Sometimes the honest answer is that a few targeted fixes beat a new codebase — and saying so is worth more than winning a bigger project.

02 — Design for the failure case

Slow networks, double-taps and half-finished work are the normal case in the field, not the exception. Local-first writes, outbox tables and idempotent submits cost far less than reconciling bad data afterwards.

03 — Leave it handover-ready

Every project ships with an architecture doc, an endpoint contract and a status file. If I disappear tomorrow, the next person starts on day one — and so do the AI agents I pair with.
