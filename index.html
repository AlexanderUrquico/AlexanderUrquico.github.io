Inventory management

Stack

Stock counting, receiving, transfers, batch picking and store-to-store approvals for four roles: branch, warehouse, distribution and audit. The role you sign in with decides which screens exist at all.

Counted lines go into the phone's own database and stay there until the ERP accepts them. A dropped connection mid-aisle costs nobody their count. Sign-in works offline too, against users synced to the handset, with bcrypt hashing running in a background isolate so the screen doesn't freeze.

Built since August 2026

  • A report queue for unscannable barcodes. It works out the cause from what the scanner actually saw (a damaged label, or an item missing from the ERP) instead of from the counter's answer, which proved unreliable.
  • Expected stock per branch, cached and usable offline. If a unit conversion isn't certain, it shows the ERP's own figure rather than a wrong one.
  • A minimum-version gate that blocks outdated builds without locking out phones that are offline.
  • Sentry monitoring of errors and failed uploads, tagged by branch, role and workflow, with no personal data.
LimitsMost screens still read the database directly. Only the newer features are built as separate services. Uploads have no duplicate protection and are retried by hand.

Branch staff photograph the bank deposit slip. The phone reads the bank, reference number, amount and date itself, and staff confirm the fields instead of typing them. It works on BDO, BPI and PNB slips.

Before this there was no system. Head office could not check a deposit until the paper slip arrived. Now it gets the slip the same day it's deposited.

OCT→0C7

A cleanup step that turned stray letters into digits also turned "OCT" into "0C7", so five months of slips had no date. The fix matches against the raw text, corrects only the number groups, and then picks from ranked date candidates. Text captured from real slips is now replayed as unit tests.

The minute-long sign-in

Sign-in on the cheap phones branches use took about a minute. The network looked guilty, but it wasn't: the API answered in 41 ms. The real cost was password hashing, at about 1.9 seconds per hash, run for all 133 cached users before anyone could sign in.

API round trip
41 ms
One password hash
1.9 s

I measured the hashing speed on the phone itself, removed the step that hashed everyone before sign-in, and set the work factor to 25,000 iterations, writing down the trade-off. Hashes now migrate both ways, so phones already in branches got faster too. Sign-in now takes under a second.

LimitsUploads need a connection; there is no offline queue. The server side, which I don't control, still uses plain HTTP without authentication. Hashing only protects the copy stored on the phone.
A-03

Warehouse transfer

Kotlin · Compose · CameraX · Room · v0.6 Test build
Role
Sole developer
Since
Aug 2026
Status
Pre-pilot, on live requests in a test environment
Tests
182
Stack
Kotlin, Jetpack Compose, CameraX, ML Kit barcode, Room, T-SQL, n8n, SAP Service Layer

A replacement for the transfer module of an old desktop app, built for warehouse checkers who walk the aisles, unlike the desktop PC.

Before building anything, I audited the old system and found two production bugs. A quantity check read the requested amount instead of the remaining amount, so a half-picked line could be picked again past its total. And on a slow connection, tapping submit twice created two real stock documents.

The new app scans barcodes with the camera against an offline list of about 7,000 items, shows quantities in the checker's own unit, offers batches by nearest expiry, and posts to the ERP with retry. Each submission gets a key on the phone that is resent on every retry, and a pending-post record survives the app being killed between submit and post.

    Practice

    How the work above got done
    01

    Read the system before rewriting it

    I check what the existing system actually does, and write it down, before proposing a replacement. A straight port would have carried both of the old transfer app's bugs across.

    Applied in A-03
    02

    Measure before fixing

    The obvious suspect is often innocent. The slow sign-in looked like a network problem, but it was hashing, and I only found that by timing each step on the phone itself.

    Applied in A-02
    03

    Design for the failure case

    Weak signal, double taps and half-finished work are normal on a warehouse floor. Saving on the phone first and making submits safe to repeat costs far less than cleaning up bad data later.

    Applied in A-01 · A-03
    04

    Every fixed bug gets a test

    A bug that's fixed but not tested comes back. Real slip photos are replayed as test data, and the wiped-picks bug has a test that fails if the old code returns. The three apps have 387 tests between them.

    Applied in A-02 · A-03
